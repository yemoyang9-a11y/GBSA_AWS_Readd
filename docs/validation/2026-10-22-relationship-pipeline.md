# 인물관계도 파이프라인 변경 및 검증 — 2026-10-22

관계의 방향·구체적인 설명·원문 근거·시점·불확실성을 생성 후보부터 저장/조회/화면까지 전달하도록 수정했다. 기존 모바일 대응을 보존했다. **전체 완료 판정은 보류한다.** 실제 모델 호출이 `401 invalid_api_key`로 실패하여 모델 산출물이 없고, 운영 데이터의 재생성·교체·배포도 수행하지 않았다.

## 원인과 확인한 실제 사례

- 기존 관계는 인물 A/B, 짧은 라벨, 확립 페이지만 저장했다. A/B를 UUID 순으로 정렬하므로 저장 순서는 감정/행동 방향을 의미하지 않았다.
- 생성 후 병합과 SQL 조회가 인물 쌍의 최신 관계 하나만 선택하여 동시 관계를 잃었다. 김씨의 질투와 혼인 주선을 최신 한 행으로 합치면 질투가 사라진 것으로 오해할 수 있다.
- 화면에는 방향·상태·근거가 없고, 같은 두 인물의 선/라벨 키가 충돌했다. 최신 관계만 받은 상태로 되감아 과거 관계를 복원할 수도 없었다.
- 정확한 원문 인용이 있어도 관계 해석 자체가 옳다는 보장은 없었다. 예전 라벨에 대한 검수 기록이 변경된 의미까지 승인하는 문제도 있었다.

| 기존 실제 데이터 | 원문으로 확인한 의미 | 새 형식으로 검증한 표시 |
| --- | --- | --- |
| 탁류 R078, 129p: `욕망` | 형보가 초봉이를 탐냄. 초봉이의 상호 감정은 근거 없음 | **형보 → 초봉이 · 일방적으로 탐냄**, 설명과 129p 원문 인용 |
| 탁류 R057, 91p: `경쟁 관계(질투의 대상)` | 김씨가 태수를 두고 초봉이를 질투 | **김씨 → 초봉이 · 태수를 두고 질투**, 설명과 91p 원문 인용 |
| 같은 쌍의 중매/질투 | 다른 종류의 관계가 동시에 존재할 수 있음 | 서로 다른 관계 이력·곡선·상세 카드 |

이는 운영 DB를 수정했다는 뜻이 아니다. 첫 두 표현은 독립 평가자가 실제 원문으로 작성한 후보를 제품의 검증/병합/등록/조회 코드에 통과시키고 화면에서 확인한 결과다. 원문 위치·기대 결과는 [독립 평가 자료](../../evaluation/relationships/README.md)에 있다.

## 핵심 변경 파일

- `backend/src/batch/pipeline/generate.ts`, `grounding.ts`: 의미 v2 구조화 출력, 구체적인 술어/방향/귀속/시점/정확한 원문 근거 검사. 오래된 생성 캐시 거절.
- `accumulate.ts`, `check-integrity.ts`: 인물 정렬에 따른 방향 반전, 독립 관계별 이력, 단발 사건 보존.
- `register.ts`, `review.ts`, 등록/검수 실행 스크립트: 의미 전체에 묶인 검수 기록, 변경 시 공개 상태 무효화, 전체 원문 범위가 확인된 관계 스냅샷 교체와 변경 기록.
- `backend/migrations/006_relationship_semantics.sql`, `backend/src/shared/types.ts`: 의미·원문 근거·검수 스냅샷 데이터 계약.
- `backend/src/modules/ssabi/pg-repository.ts`, `relationship-versions.ts`, API: 인물/관계/원문 근거를 서버 읽기 범위로 제한한 다음 의미별 최신 상태 선택. 제한된 이력과 별칭 공개 시점을 전달. 그래프 응답은 `no-store`.
- `backend/src/modules/chatbot/repository.ts`, `context-assembly.ts`: 같은 원문 범위와 관계 방향·귀속을 챗봇 문맥에도 보존.
- `frontend/src/components/Ssabi/RelationshipGraph.tsx`, `RelationshipDetails.tsx`, `graphEdges.ts`, `graphFilter.ts`, `graphLayout.ts`: 방향 화살표, 복수 관계, 구체적인 설명·불확실성·원문 펼치기, 되감기. 기존 데이터는 방향을 추측하지 않고 `방향 미검증`으로 표시.
- 재사용 실행 방법과 검수/교체 절차: [파이프라인 사용 문서](../relationship-pipeline.md).

## 검증 범위와 증거

1. **단위/회귀 검사:** 백엔드 68개 suite/631개 테스트, 프런트엔드 66개 파일/415개 테스트, 양쪽 production build 통과. 변경한 제품 소스의 lint 오류는 없다. 백엔드 ESLint 설정은 테스트 파일을 tsconfig에서 제외하므로 테스트까지 강제로 포함한 lint 실행은 설정 오류 6건이었다(테스트 TypeScript는 Jest로 검사됨). 기존 프런트엔드 전체 lint에는 `useSSE.position.test.ts:56`의 `require-yield` 오류가 남아 있으며 이번 수정과 무관하다.
2. **실제 로컬 SQL:** PGlite의 PostgreSQL 엔진에 실제 migration과 제품 등록/조회 함수를 실행. 방향 정렬, 반대 방향/동시 관계, 단발 사건, 과거 이력, 미래 근거/인물 차단 검사. 기존 baseline schema에서 관계와 무관한 vector 확장/컬럼/인덱스만 제외했다. 운영 PostgreSQL에 접속하거나 쓰지 않았다.
3. **실제 원문을 쓴 후보 흐름:** 탁류 91p/129p, Austen의 질투·질투 부정·인물 믿음 발췌, 총 5개 원문 창/6개 관계. 사람이 작성한 후보 → 제품 검증기 → 병합 → 등록 → 로컬 SQL → 제품 그래프 조회 → 실제 UI. 6개 관계의 인물/방향/설명/원문/확정 상태가 보존됐다. 확립 직전에는 0건, 해당 시점에는 기대 관계가 표시되는 양쪽 경계를 검사했다. 전체 인물 추출이나 모델 추출 정확도 검증은 아니다.
4. **브라우저:** Chromium, 390×844와 1440×1000에서 실제 관계도 컴포넌트 실행. 위 5개 원문 창 × 2개 화면 크기에서 방향/부정/믿음 귀속/원문을 확인했다. 별도 복수 관계·되감기·늦은 별칭 시나리오도 두 크기에서 확인. iPhone/Android 태블릿/PC 프리셋의 기존 읽기·사이드바·전체화면 회귀 8건도 통과했다(320px iPhone 세로/가로 포함). 실제 iOS Safari/물리 Android 검증은 아니다.
5. **독립 평가:** 제품 구현에 참여하지 않은 `relationship_evaluator`가 먼저 원문 oracle를 작성하고, 후보/SQL/화면을 별도로 검사했다. 검수 승인 재사용과 다른 책 ID 충돌 같은 결함을 찾아 수정 후 재검사했다. [최종 독립 평가](../../evaluation/relationships/final-evaluation.md).

원문 위치·출처 해시·후보/결과·화면·독립 검사 스크립트는 `evaluation/relationships/`에 보존했다. Austen 페이지 1은 발췌 테스트의 번호이며 실제 책의 인쇄 페이지가 아니다. 평가용 창작 문장은 실제 다른 작품 실적으로 계산하지 않았다. 한 번 수정에 사용한 held-out 사례를 계속 미사용 표본이라고 표현하지 않는다.

독립 평가에서 발견한 두 추가 결함도 재검사했다. 관계 ID가 다른 책과 충돌하면 수정 전에 거절하고 SQL upsert에서도 책 소유권을 확인한다. 좁은 두 인물 그래프가 확대 버튼에 일부 겹치던 문제는 조작부를 별도 하단 영역에 배치해 수정했다. 실제 노드/이름과 버튼 경계의 교차가 0임을 확인했다.

대표 화면: [탁류 129p 모바일](../../evaluation/relationships/results/source-flow-takryu-p129-mobile.png), [탁류 91p 모바일](../../evaluation/relationships/results/source-flow-takryu-p91-mobile.png), [Austen 믿음 귀속 모바일](../../evaluation/relationships/results/source-flow-austen-belief-attribution-mobile.png). 모두 원문을 읽어 사람이 작성한 후보의 로컬 검증 화면이며 운영 배포 화면이 아니다. 동일 조건의 운영 배포본 수정 전/후 캡처는 없다.

## 반드시 남겨야 하는 한계

- **자동 구조 검증은 의미의 진실을 보증하지 않는다.** 잘못된 방향·부정·소문 등을 넣은 독립 후보 주입 21개 중 11개의 잘못된 확정 후보가 구조 검사만으로는 걸러지지 않았다. 이 수치는 수정 전후 같으며, 모델의 실제 추출 정확도나 정밀도로 계산하면 안 된다. 따라서 의미 검수 전 후보를 공개하지 못하도록 검수 스냅샷과 공개 차단을 유지했다.
- 실제 모델은 4개 발췌 실행과 진단 재시도에서 유효한 결과를 내지 못했다. 확인된 진단 오류는 `401 invalid_api_key`이고 **모델 출력 0개**다. [실패 기록](../../evaluation/relationships/results/live/failed-generation-report.json). 추출 누락률·보류율·모델 일반화 성능은 **미검증**이다.
- 6개 원문 후보의 저장/표시 보존은 확인했지만 작품 전체의 관계를 빠짐없이 추출했다는 뜻이 아니다. 전체 책 인물/별칭 자동 추출, 운영 DB/배포본, 실제 기기 Safari/WebKit은 **미검증**이다.
- 운영 탁류의 기존 관계는 그대로다. 전체 원문 생성 → 기존 인물 ID의 검수된 연결 → 스냅샷 교체 → 의미 검수 → 공개 절차가 남아 있다. 표본만으로 전체 관계를 교체하지 않도록 차단했다.

## 네 가지 상태

| 상태 | 항목 및 확인 범위 |
| --- | --- |
| **구현됨** | 재사용 생성 프롬프트/후보 실행기, 캐시 무효화. 실제 모델의 올바른 추출까지는 검증하지 못함 |
| **실제 검증됨** | 위 6개 원문 후보의 저장·조회·화면 의미 보존, 창작 SQL 시나리오, 읽기 경계/되감기, 검수 기록과 공개 상태 무효화. 독립 평가의 실행 증거 범위에 한함 |
| **구현 안 됨** | 원문 의미의 자동 판정만으로 잘못된 방향·추론을 모두 차단하는 기능. 현재는 별도의 원문 의미 검수가 필수이며 자동 정확성을 보증하지 않음 |
| **환경 이슈로 검사가 제한됨** | 실제 모델 생성/누락·보류 평가: API 인증 실패. 구현은 있음. 실제 기기/WebKit 검증 환경도 없어 해당 항목은 미검증 |

인증 복구 후에는 새 출력 디렉터리에서 실제 발췌 생성을 다시 실행하고, 독립 평가자가 원문과 결과·누락/보류를 비교해야 한다. 이후 전체 책 결과를 검수하여 공개한 뒤 실제 독서 화면에서 재검증해야 최종 완료 여부를 판단할 수 있다.
