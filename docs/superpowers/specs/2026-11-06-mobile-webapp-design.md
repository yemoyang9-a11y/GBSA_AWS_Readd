# 모바일 웹앱 — 완성 기준과 설계

- 작성일: 2026-11-06
- 작업 위치: Orca 워크트리 `모바일`, 브랜치 `yemoyang9-a11y/selkie`
- 근거: 2026-11-06 사용자 인터뷰(grill-me) 결정 1~19. 사용자 결정은 "결정 N", 작성자 판단은 **[작성자 판단]**으로 표시한다.

## 1. 왜 하는가

지금까지는 태블릿 가로(1133×744) 기준으로 개발했다. 이제 **휴대폰 웹앱**을 기준으로 개발한다.

사용자가 정한 완성 기준은 이것이다. **"모바일 앱처럼 쓰는 데 아무 지장이 없다."** 대표 예시는 화면을 옆으로 밀면 다음 페이지로 넘어가는 동작이다.

시작 전 확인 결과(2026-11-06): 다른 워크트리(본 체크아웃 `yemo-develop`, `pelican`, `readd-cost`, `readd-ssabi-cards`)와 main에 합쳐지지 않은 브랜치 9개 어디에도 모바일 작업은 없었다. 이번 작업은 처음부터 시작한다.

## 3. 구조

### 3.1 폴더 (결정 2)

- 같은 `frontend` 앱 안에 **`frontend/src/mobile/`**을 새로 만든다. 모바일 화면과 컴포넌트는 전부 이 안에 둔다.
- `services/`, `hooks/`, `types/`, `utils/`는 PC와 **함께 쓴다.** 이 층을 복사하지 않는다.
- 배포는 지금의 Cloudflare Pages 하나 그대로다.
- **진행 로직 공용 훅 추출 (결정 18):** 서버 호출을 언제 어떤 순서로 부르는지는 지금 PC 페이지 파일 안에 있다. 아래 로직을 공용 훅(`hooks/`)으로 옮기고, PC 페이지와 모바일 화면이 같은 훅을 쓴다. 화면 모양만 따로 그린다.
  - `Reader.tsx`: 책 진입 판정, 진도 저장, 늦게 온 페이지 응답 무시, 리캡 자동 호출 제한, 페이지 이동 시 인용 초기화, 탭 기억, 세션 유지 신호
  - `Briefing.tsx`: 목차 이동 시 진도 저장 완료를 기다린 뒤 이동하는 처리
  - `Dashboard.tsx`: 책 진입 가능 여부 판정과 진입 처리
- 추출은 **동작을 바꾸지 않는 위치 이동**이다. 옮기기 전 `npm test` 결과와 PC 스크린샷을 기준선으로 기록하고, 옮긴 뒤 같은지 확인한다(P1·P2).
- 이 추출과 라우트 연결 지점(App의 라우트 정의) 외에는 PC 화면 파일(`pages/*`, `components/*`)을 수정하지 않는다.
- 모바일 화면이 PC 컴포넌트 중 기존 그대로 쓸 수 있는 것(예: 싸비 탭 내부, 관계도 그래프)을 import해 쓰는 것은 허용한다. 다만 그 파일을 고쳐야 할 때는 PC 화면이 바뀌지 않는다는 것을 PC 테스트로 확인한다. **[작성자 판단]**

### 3.2 모바일 화면 선택 (결정 3)

- 주소는 PC와 같다(`/`, `/books/:bookId/briefing`, `/books/:bookId/read`, `*`).
- 화면의 **짧은 쪽 길이가 600px 미만인 기기**(`screen.width`와 `screen.height` 중 작은 값)이면 모바일 화면을 그린다. 창 폭으로는 판단하지 않는다.
- 이렇게 하면 iPhone을 눕혀도 모바일 화면이 유지되고, PC 브라우저 창을 좁혀도 PC 화면이 유지된다. Chrome 개발자 도구의 기기 흉내 모드는 화면 크기 자체를 흉내 내므로 이 방식으로도 확인할 수 있다.
- 화면이 열려 있는 동안 판단이 바뀌어도 화면을 전환하지 않는다. 판단은 앱이 시작될 때 한 번 한다. **[작성자 판단]**

### 3.3 그대로 지키는 프로젝트 규칙

모바일 화면도 `CLAUDE.md`의 절대 규칙과 불변식을 그대로 따른다. 이번 작업에 직접 걸리는 규칙은 아래와 같다.

- **절대 규칙 10번:** 프론트에서 페이지를 다시 나누지 않는다. 휴대폰 폭에서는 한 페이지의 스크롤 길이만 늘어난다.
- **절대 규칙 9번:** 페이지 안에서 위아래로 스크롤해도 서버 이벤트가 생기지 않는다. 스와이프 넘김은 "페이지 이동"이므로 이벤트가 생긴다.
- **스와이프의 이동 대상:** 서버가 준 `prev_page`·`next_page`만 쓴다. 지금 "이전/다음 페이지" 버튼과 같은 이동 경로(`onMove`)를 탄다.
- **절대 규칙 2·8번:** 프론트에서 기준점이나 %를 계산하지 않고, 기준점을 서버에 보내지 않는다.
- **R3·FR-NAV-001:** 목차는 상한 없이 전체를 보여 준다.
- **로그:** 모바일은 PC와 같은 `services`를 쓰므로 로그 적재 경로가 같아야 한다. 새 서버 호출 경로를 만들지 않는다.

## 4. 화면별 동작

### 4.1 읽기 화면 — 페이지 넘김 (결정 4·5)

- **방향:** 손가락을 오른쪽에서 왼쪽으로 밀면 다음 페이지, 왼쪽에서 오른쪽으로 밀면 이전 페이지.
- **느낌:** 손가락을 따라 본문이 옆으로 끌려간다. 손을 뗐을 때 화면 폭의 1/4 이상 밀었거나 빠르게 튕겼으면 넘어가고, 아니면 제자리로 돌아온다.
- **효과:** 옆으로 미끄러지는 효과만 둔다. 책장을 넘기는 3D 효과는 없다.
- **끝 페이지:** 첫 페이지에서 이전으로, 마지막 페이지에서 다음으로 밀면 살짝 끌렸다가 튕겨 돌아온다.
- **기존 조작:** 맨 아래 "이전/다음" 버튼과 페이지 번호 입력은 유지한다.
- **넣지 않는 것:** 화면 좌우 끝을 톡 쳐서 넘기는 방식.
- **인용 선택:**
  - 바로 밀기는 페이지 넘김이다.
  - 꾹 눌러서 문장을 고르면 iOS 기본 선택 손잡이로 범위를 조절한다. 선택 영역 **아래쪽**에 "챗봇에 물어보기" 버튼이 뜬다. iOS가 선택 영역 위에 띄우는 자체 메뉴와 겹치지 않게 하기 위해서다.
  - 그 버튼을 누르면 싸비 챗봇이 열리고 선택한 문장이 인용으로 붙는다.
  - 글자가 선택된 동안에는 스와이프 넘김이 멈춘다. 선택을 풀면 다시 넘길 수 있다.
- **iPhone Safari 제약:** 화면 왼쪽 끝에서 밀면 브라우저 "뒤로 가기"가 실행되고, 우리 앱이 막을 수 없다. 그래서 스와이프는 본문 가운데 쪽에서 시작하는 것을 기준으로 동작을 보장한다.

### 4.2 읽기 화면 — 양옆 손잡이 (결정 6·7)

- 옛 페이스북 메신저 "채팅 헤드"를 모델로 한다. **왼쪽 가장자리에는 목차, 오른쪽 가장자리에는 싸비** 손잡이가 하나씩 떠 있다.
- 손잡이는 작게 살짝 튀어나와, 있다는 건 알 수 있지만 읽는 데 거슬리지 않는 정도다.
- 위치는 고정한다. 높이는 엄지가 닿는 곳, 즉 세로 가운데보다 약간 아래다. 끌어서 옮기는 기능은 없다.
- 반투명으로 하고, 본문 글줄이 손잡이 아래로 오지 않도록 좌우 여백을 손잡이 크기만큼 둔다.
- **여닫기:** 손잡이를 누르면 열린다. 열린 상태에서도 같은 모양의 손잡이가 그대로 보이고, 다시 누르면 닫혀 읽던 페이지로 돌아온다. 밀어서 닫는 동작은 없다.
- 손잡이의 정확한 크기·모양·색은 스크린샷을 보고 확정한다(결정 17).

### 4.3 읽기 화면 — 목차 리스트 (결정 8·9)

- 목차는 창이나 패널이 아니다. **왼쪽 손잡이 자리에서 장 목록이 작게 "촤르륵" 펼쳐지는 리스트**이고, 스크롤할 수 있다.
- 폭은 **반드시 화면의 50% 미만**이다. 본문이 계속 보여야 하며, 목적은 "지금 어느 장인지 확인" 정도다.
- 지금 읽는 장을 강조하고, 열릴 때 그 장이 보이는 위치로 스크롤한다.
- 장을 누르면 그 장 첫 페이지로 이동하고 리스트가 닫힌다. PC와 같은 동작이다(`Reader.tsx` `handleSelectChapter`).
- 리스트가 열려 있어도 본문 스크롤과 스와이프 넘김은 동작한다. 장이 바뀌면 리스트의 강조도 바뀐다.
- 정확한 크기와 모양은 실제 화면을 보고 확정한다(결정 8).

### 4.4 싸비 (결정 6·14·15·16)

- **화면 전체(100%)**로 열린다. 지금은 화면의 약 70%만 덮는다(사용자 관찰).
- **탭:** 맨 위에 리캡·관계도·챗봇 탭 막대를 둔다. **PC와 같은 포스트잇 탭 모양**을 쓰고(`SsabiPanel.tsx`의 tablist), 높이는 최소 44px이다. 탭은 눌러서만 바꾸고, 옆으로 밀어서 바꾸는 동작은 없다.
- 다시 열면 마지막에 보던 탭이 열린다. PC와 같다.
- **챗봇 입력창:** Claude·ChatGPT 모바일 앱의 동작 방식을 따른다. 브랜딩은 따라 하지 않는다.
  - 입력 중: 입력창이 키보드 바로 위에 붙는다. 글이 길어지면 여러 줄로 늘어나다가 5~6줄을 넘으면 입력창 안에서 스크롤된다. 보내기 버튼은 입력창 오른쪽 안에 있고, 글자가 있을 때만 활성화된다. 대화 영역만 줄어들고 최신 답변이 보이게 유지된다. 대화 영역을 누르거나 아래로 쓸어내리면 키보드가 내려간다. 화면 전체가 위로 밀려 올라가지 않는다.
  - 입력 밖: 화면 맨 아래에 한 줄짜리 둥근 입력창만 남고, 홈 막대 영역만큼 아래 여백을 둔다.
  - 입력창 글자는 16px 이상이다. iOS가 자동으로 화면을 확대하지 않게 하기 위해서다.
  - 키보드가 떠 있는 동안 오른쪽 싸비 손잡이는 숨긴다.
- **관계도:**
  - 한 손가락으로 끌면 그래프가 움직이고, 두 손가락으로 벌리거나 오므리면 그래프만 확대·축소된다. 이때 Safari의 화면 확대는 막는다.
  - 인물을 누르면 관계 설명이 나온다.
  - 확대·축소·전체 보기 버튼과 **전체화면 버튼은 모두 유지한다.** 전체화면은 그래프만 휴대폰 화면 전체에 띄우는 기능이다.

### 4.5 브리핑, 서재, 404·오류 (결정 11·17)

- 구체적인 배치는 정하지 않았다. 화면을 하나씩 만들 때 스크린샷으로 정한다.
- 출발 안은 이렇다. 서재는 책 카드 3열을 1열 목록으로 바꾸고, 책 정보 팝업은 아래에서 올라오는 시트로 바꾼다. **[작성자 판단 — 스크린샷으로 확정]**
- 브리핑의 저장 리캡, 목차 위치, 진도 막대, '마저 읽기' 구성은 PC와 같다. %·진도 값은 서버에서 받은 값만 쓴다.

## 5. 완성 기준

### 5.1 진행 방식 (결정 17)

1. 읽기 화면을 만들고 iPhone 세로 흉내 스크린샷을 보여 준 뒤, 피드백을 반영해 확정한다.
2. 같은 방식으로 싸비 → 브리핑 → 서재 → 나머지 순서로 화면마다 "만들기 → 스크린샷 → 피드백"을 반복한다.
3. 전 화면이 끝나면 아래 자동 점검을 한 번에 돌리고, "실기기 미확인" 목록을 붙여 완성 보고를 한다.

### 5.2 자동 점검 — 이것을 통과하면 완성 (결정 12·13)

- **도구:** Playwright, WebKit 엔진, iPhone 세로 기기 설정. 개발 의존성으로만 설치한다(설치 허락: 결정 12).
- **크기:** 375px과 430px 두 가지로 돌린다. **[작성자 판단]**
- **서버 (결정 19):** 앱은 실제 API 경로로 요청을 보내고(`VITE_USE_MOCK=false`), **Playwright가 요청을 가로채 점검용 응답을 돌려준다.** 앱 내장 대역(`mocks/server.ts`)은 네트워크 요청을 만들지 않아 요청 횟수를 셀 수 없기 때문이다. 점검용 응답 데이터를 새로 만들어, 첫 페이지·마지막 페이지·장 경계·오류 응답 상태를 만들 수 있게 한다. 운영 서버와 운영 DB는 쓰지 않는다.

### 5.3 마지막 실제 연결 확인 1회 (결정 19)

- 전 화면이 끝나면 로컬 백엔드와 로컬 DB(Docker `readd-pg`)를 띄운다. 그리고 iPhone 흉내 화면에서 서재 → 브리핑 → 읽기(스와이프 넘김) → 싸비 3탭 흐름을 한 번 실제로 지나간다.
- 진도 레코드가 로컬 DB에 실제로 쌓이는지 확인한다.
- 로컬 DB에 「탁류」 데이터가 없으면 채울지 사용자에게 묻는다. 리캡·챗봇의 실제 AI 호출 여부도 비용 때문에 그때 묻는다.
- 본 체크아웃의 `backend/.env`는 운영 Supabase를 가리키므로 쓰지 않는다.

### 5.4 실기기 미확인 — 완성 보고에 따로 표시 (결정 13)

아래는 자동 점검으로 확인할 수 없다. 완성 보고에 "실기기 미확인"으로 표시하고, 사용자가 iPhone으로 써 보다가 문제가 보이면 그때 고친다.

1. 홈 화면 아이콘으로 열었을 때 주소창 없이 전체 화면으로 뜨는지, 실제 노치·홈 막대와 겹치지 않는지
2. Safari의 "왼쪽 끝에서 밀면 뒤로 가기"가 왼쪽 손잡이·스와이프와 부딪히는지. 홈 화면 모드에서는 이 동작이 없을 것으로 예상하지만 확인하지 않았다
3. 꾹 눌렀을 때 뜨는 iOS 메뉴와 "챗봇에 물어보기" 버튼의 실제 위치 관계
4. 스와이프의 손맛(끌림, 튕김 세기)과 실제 키보드가 움직이는 모습
5. 로컬 주소(http)로 홈 화면에 추가했을 때 전체 화면으로 뜨는지(모름). 안 되면 Cloudflare 미리보기 사용 여부를 사용자에게 묻는다. 브랜치 push는 사용자가 허락할 때만 한다

## 6. 하지 않는 것

- 가로 화면 다듬기, Android 확인, 태블릿·PC 화면 변경
- 오프라인 기능, 네이티브 앱
- 화면 끝을 톡 쳐서 넘기기, 손잡이 끌어 옮기기, 옆으로 밀어 싸비 탭 바꾸기, 밀어서 싸비 닫기
- 책장 넘김 3D 효과
- 서버 API·스키마 변경. 모바일은 기존 API만 쓴다

## 7. 만드는 사람이 정할 것

- 스와이프 판정 세부 값: 빠른 튕김 속도 기준, 가로·세로 방향 판정 각도, 꾹 누르기와 밀기 구분 시간
- 손잡이·목차 리스트·서재·브리핑의 시각 세부. 단, 기존 디자인 토큰을 쓰고 스크린샷 피드백으로 확정한다
- 키보드 흉내 방식. `visualViewport` 크기를 조절하는 등의 방법
- Playwright 설정 파일 위치와 점검 스크립트 구조

## 8. 확인할 사실

- `index.html`이 Google Fonts에서 `Pretendard`를 요청하고 있다. Google Fonts가 이 글꼴을 제공하지 않으면 다른 글꼴로 대체된다. C5 점검 때 iPhone 흉내 환경에서 실제로 어떤 글꼴이 쓰이는지 확인한다.
- 로컬 DB 컨테이너 `readd-pg`(pgvector, PostgreSQL 17)가 떠 있다. 이 프로젝트용인지, 「탁류」 데이터가 들어 있는지는 확인하지 않았다.
- 작업 위치 `frontend`에 `node_modules`가 없다. 첫 단계에서 `npm install`로 기존 의존성을 설치하고 P1 기준선을 기록한다.
