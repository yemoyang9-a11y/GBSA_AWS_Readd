## 2. 동결 계약 — CP0에서 확정하고 이후 변경 금지

### 2.1 기준점 스냅샷 인터페이스 (R2 제공, ③④⑤ 소비)

```
getCutoffSnapshot(deviceId, bookId) -> {
    current_page,   // 저장값. 마지막으로 열어본 페이지
    cutoff,         // current_page - 1        (FR-PRG-003 🚦)
    percent,        // current_page / total_pages
    chapter         // current_page가 속한 장
}
```

**이 함수 바깥에서 `page - 1`이나 `%`를 계산하는 코드는 존재해서는 안 된다.** 프론트도 서버가 내려준 값을 그대로 렌더한다. FR-BRF-005 🚦(불일치 0건)은 검증이 아니라 **계산 지점 단일화로** 달성한다(3.3절).

각 요청은 시작 시 스냅샷을 **1회** 받아 요청 내 모든 쿼리·조립·로그가 그 값을 쓴다. 질의 도중 페이지가 바뀌어도 그 요청은 시작 시점 기준점을 유지한다(UC-27 A5).

### 2.2 리포지토리 시그니처 규칙 (FR-SPL-002 🚦의 코드 수준 강제)

상한이 걸리는 저장소 접근은 **전부** 아래 형태를 갖는다.

```
findX(bookId, cutoff, ...)      // cutoff 인자가 없는 조회 함수는 만들지 않는다
```

cutoff를 적용하지 않은 원시 쿼리를 도메인 코드에 노출하지 않는다(4.3절). 파이프라인(⑦)만 예외 — 쓰기 주체이고 상한 개념이 없다.

### 2.3 클라이언트가 보낼 수 있는 것

**"기준점"을 직접 보내는 API는 존재하지 않는다.** 클라이언트가 보낼 수 있는 건 진도 이벤트 `{page, seq}`뿐이다. `seq`는 클라이언트 단조 증가 시퀀스이며, 서버는 **더 새로운 seq일 때만** 수용한다.

### 2.4 로그 계약 (게이트 판정의 근거 — 5.1.3절)

| 로그 | 필수 필드 | 게이트 |
| --- | --- | --- |
| 리캡 호출 로그 | 기준점 페이지, 투입 장 요약 ID 목록, 현재 장 절단 페이지, 출력 참조, 모델·토큰, 트리거(실시간/세션종료) | NFR-OBS-002 🚦 |
| 챗봇 질의 로그 | 기준점 페이지, 투입 레코드 ID **전수**(장 요약/원문 페이지/엔티티/배경지식 구분), **검색 선정 페이지**, 근거 부재 여부, 선택 모델, 출력 참조, 토큰 | NFR-OBS-005 🚦 |
| 조회 응답 | 응답 payload에 **페이지 값 필드 포함** (별도 테이블 아님) | NFR-OBS-003 |

**로그가 없으면 게이트 판정이 불가능하다.** 기능이 동작해도 로그가 비면 통과를 증명할 수 없다.

### 2.5 API 엔드포인트 (4.2절)

| 엔드포인트 | 담당 |
| --- | --- |
| `GET /books` · `GET /books/{b}/info` · `GET /books/{b}/pages/{n}` | R4 |
| `POST /books/{b}/entry` · `POST /books/{b}/progress` · `POST /books/{b}/heartbeat` | R2 |
| `GET /books/{b}/briefing` · `POST /books/{b}/recap/stream` | R2 |
| `GET /books/{b}/ssabi/graph` · `GET /books/{b}/ssabi/characters/{c}` | R4 |
| `POST /books/{b}/chat` | R3 |
| `GET /books/{b}/ssabi/glossary`, `/timeline` | **[이후 확장]** — 만들지 않는다 |

조회 요청은 `(page, seq)`를 동봉할 수 있고, 서버는 이를 **진도 이벤트와 동일하게** 처리한 뒤 기준점을 파생한다(3.3절).

## 3. 시드 데이터 (CP0에서 함께 만든다)

파이프라인 완주(8/21) 전까지 R2·R3·R4가 개발할 근거다. 3~5장 분량이면 충분하다.

| 테이블 | 최소 수량 |
| --- | --- |
| 페이지 | 20~30 |
| 장 경계 · 장 요약 | 3 |
| 인물 | 5 |
| 인물 별칭 | 10 (유형 4종이 섞이도록) |
| 관계 | 5 |
| 인물 노트 | 10 |
| 용어 · 사건 | 각 5 |
| 배경지식 · 소개 | 각 1 |

**반드시 넣을 3가지** — 없으면 상한 로직이 도는지 눈으로 확인할 수 없다.

1. **확립 페이지가 뒤쪽인 관계 1개** — 앞 기준점에서 안 보여야 한다 (FR-SPL-002 🚦)
2. **후반부에 처음 나오는 가족관계 호칭 별칭 1개** — 별칭이 관계 누설의 옆문이 되는지 확인 (D6)
3. **라벨이 바뀌는 관계 1쌍**(같은 쌍, 확립 페이지 다른 2행) — 표시는 최신 1개, 챗봇 근거는 이력 전체 (A6)
