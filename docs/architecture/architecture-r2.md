## 1. 배포 형상 요약

```

              정적 자산 │        │ API · SSE (캐시 비활성)
                  ┌─────▼───┐    │

   │  │       └ ssabi-sweeper    │  │       └ ssabi-sweeper  │  │
   │  │   수동 ─ ⑦ 파이프라인    │  │   (배치는 #1에서만)     │  │
   │  │          ⑧ 평가 하네스   │  │                        │  │

   │  ┌── 프라이빗 AZ-a / AZ-c ▼─────────────────────────────┐   │
   │  │  RDS PostgreSQL + pgvector (db.t4g.micro)           │   │
   │  │   Multi-AZ — AZ-a 주 / AZ-c 대기, 자동 장애 조치      │   │
   │  │   DB 2개: ssabi / ssabi_dev                          │   │
   │  └──────────────────────────────────────────────────────┘   │
   └─────────────────────────────────────────────────────────────┘

                    └────────────────┘

```

**핵심 성질 4가지**

1. **배포 단위는 여전히 1개다.** r1 4.8절의 "모듈러 모놀리스 + 실행 단위 2개"를 유지하되, 실행 단위를 서로 다른 *서비스*가 아니라 **같은 이미지·같은 코드의 다른 프로세스**로 실현한다(2.2절). 인스턴스가 2대가 되어도 배포 대상은 하나의 산출물이다.
2. **AZ 단위 이중화.** EC2 2대를 AZ-a·AZ-c에 나누고 ALB가 앞에 선다. RDS도 Multi-AZ다 — **한쪽만 이중화하면 이중화가 아니기 때문이다**(2.7절).
3. **애플리케이션이 무상태라서 2대가 가능하다.** 상태는 전부 RDS에 있고, 세션 리캡 캐시도 DB 테이블이다(2.6절). 어느 인스턴스가 요청을 받아도 같은 결과가 나온다 — 스티키 세션이 필요 없다.
4. **클라이언트가 보는 오리진은 하나다.** CloudFront 배포 1개가 정적 자산과 API를 모두 받으므로 **CORS 설정이 필요 없고**, TLS 종단이 한 곳이다. 프리플라이트가 사라지는 것은 `X-Device-Id` 커스텀 헤더를 쓰는 지금 계약에서 특히 이득이다 — 교차 오리진이면 커스텀 헤더 때문에 모든 요청에 OPTIONS가 선행한다.

### 2.1 리전 — 서울 단일 **[확정]**

> **8/21 확정** — Bedrock 모델 접근이 **서울(ap-northeast-2)에 열려 있음**을 확인했다. 전 리소스를 서울 단일 리전에 둔다. Bedrock 호출만 미국으로 분리하는 안(아래 대안)은 **불필요해졌다.** 대신 아래의 모델 ID 문제는 그대로 남는다.

TECH_STACK.md는 두 곳에서 서로 호출 불가능한 조합을 적어놓았다.

| 위치 | 값 |
| --- | --- |
| "리전 선택 — 확정" | `ap-northeast-2` (서울) |
| 프로덕션 `.env` 예시 | `AWS_REGION=us-east-1` |
| 모델 ID | `us.anthropic.claude-sonnet-4-5-...` / `us.anthropic.claude-haiku-4-5-...` |

`us.` 프리픽스는 **미국 리전 교차추론 프로필**이다. 서울 리전 클라이언트로 이 ID를 호출하면 실패한다. 개발 중에는 각자 `.env`가 `us-east-1`이라 안 터졌을 가능성이 크고, 배포에서 처음 드러난다.

> **[정정 — 8/21 재검토, `feature/R2-core` 대조는 stale이었음]** 위 표는 TECH_STACK.md의 예시만 보고 쓴 것이다. 코드 대조를 처음 `feature/R2-core`로 했는데, 그 브랜치가 develop의 최신 수정을 안 당겨간 상태였다 — 대조를 `develop`/`main` 기준으로 다시 했다:
> - 루트 `.env.example`(`main`·`develop`·전 feature 브랜치에 **동일하게 존재**, 마지막 수정 `d6e105a` 8/20 12:58) — `AWS_REGION=ap-northeast-2` · 모델 ID는 `us.`가 아니라 **`global.anthropic.claude-sonnet-4-5-...` / `global.anthropic.claude-haiku-4-5-...`**
> - `backend/.env.example`(`develop` 기준, 마지막 수정 `daf43e0` 8/20 15:55, R1의 dotenv 수정 PR) — 이미 루트 파일과 **동일한 값**(`ap-northeast-2` + `global.`)으로 교체됐고, `global.` 프리픽스로 실호출 검증 완료했다는 주석(2026-08-20, R1)까지 남겨뒀다. 11장 16번(두 파일 값 불일치)은 **`develop` 기준으로는 이미 해소**다.
> - 다만 **`feature/R2-core`는 아직 이 수정을 안 당겨간 구버전**(`us-east-1` + 프리픽스 없는 구모델 `claude-sonnet-3-5`)이다. R2 브랜치에서 배포 준비를 한다면 develop을 먼저 merge/rebase해야 한다 — 이번 v0.5에서 "16번 신규 발견"이라고 쓴 건 R2-core 기준으로는 맞는 관찰이었지만, develop 기준으로는 이미 닫힌 항목이었다는 걸 이번에 알았다.
>
> **`global.`이 서울에서 실제로 되는지도 코드 주석에만 의존하지 않고 8/21 직접 재확인했다** — `aws bedrock list-inference-profiles --region ap-northeast-2`에 `global.anthropic.claude-sonnet-4-5-20250929-v1:0` / `global.anthropic.claude-haiku-4-5-20251001-v1:0`이 실제로 뜨고, `invoke-model`로 Haiku를 호출해 정상 응답(`"Pong! 👋"`)까지 받았다. **`apac.` 교체는 불필요하다.** 아래 "전부 서울" 표를 이 결과로 정정한다.

**확정 — 전부 서울.**

| 항목 | 값 |
| --- | --- |
| EC2 · RDS · S3 · CloudWatch · Bedrock | **`ap-northeast-2`** |
| 모델 ID 프리픽스 | **`global.`** — 8/21 서울 리전 실호출 검증 완료(아래). `apac.` 교체는 불필요, **현재 값 유지** |
| ACM 인증서 (B안 승격 시에만) | `us-east-1` — CloudFront 요구사항이라 **여기만 예외** |

교차 리전 호출이 없어지면서 첫 토큰 지연에서 태평양 왕복(약 150~200ms)이 빠진다. NFR-PERF-002(2.0초/3.0초)·008의 예산이 그만큼 넉넉해졌다 — B-1 프롬프트가 완독 직전에 커지는 걸 고려하면 **적지 않은 여유**다.

**모델 ID — 해소 (8/21, 실호출로 검증)**

`us.` 프리픽스는 TECH_STACK.md 예시에만 있었고 실제 코드(`develop` 기준)엔 처음부터 없었다. `global.`이 실제로 서울에서 되는지가 유일하게 남은 불확실성이었는데, 직접 실행해서 확인했다:

```bash
$ aws bedrock list-inference-profiles --region ap-northeast-2 \
  --query 'inferenceProfileSummaries[?contains(inferenceProfileId, `claude-sonnet-4-5`) || contains(inferenceProfileId, `claude-haiku-4-5`)].inferenceProfileId'
[
  "global.anthropic.claude-sonnet-4-5-20250929-v1:0",
  "global.anthropic.claude-haiku-4-5-20251001-v1:0"
]

$ aws bedrock-runtime invoke-model --region ap-northeast-2 \
  --model-id "global.anthropic.claude-haiku-4-5-20251001-v1:0" \
  --body '{"anthropic_version":"bedrock-2023-05-31","max_tokens":10,"messages":[{"role":"user","content":"ping"}]}' \
  --cli-binary-format raw-in-base64-out /tmp/out.json
# 응답: {"content":[{"type":"text","text":"Pong! 👋\n\nI'm"}], ...} — 정상 성공
```

**해야 할 일은 모델 ID 교체가 아니라 `feature/R2-core`가 develop을 따라잡는 것뿐이다.**

> **코드 영향 — 해소 확인 (8/21)** — 게이트웨이(⑥)가 모델 ID를 환경변수로 받는지 확인했다. `gateway.ts`는 `model-config.ts`의 `getModelForTask()`를 거치고, 그 안의 `MODEL_CONFIG`는 전부 `process.env.BEDROCK_CLAUDE_SONNET` / `BEDROCK_CLAUDE_HAIKU` 참조다 — 하드코딩된 모델 ID는 없다. 이 항목은 닫는다. 리전은 서울 단일로 확정됐으므로 `BEDROCK_REGION` 분리는 이제 불필요하다 — `AWS_REGION` 하나로 충분하다.

> **NFR-AI-002(모델 버전 고정)** — 이번엔 모델 ID를 바꾈 일이 없었으므로(원래도 `global.`이었다) 가드레일 재수행 트리거가 아니다. 이 조항은 **실제로 프리픽스를 교체하는 날**을 위해 남겨둔다 — 교차 리전 프로필과 지역 프로필은 뒤에 붙는 실제 모델이 같더라도 라우팅되는 리전이 다르므로, 그런 변경이 생기면 CP5(8/25) 이전에 가드레일을 재수행해야 한다.

### 2.2 스위퍼를 Lambda로 만들지 않는다 **[확정 제안 — TECH_STACK 변경]**

TECH_STACK.md는 "EventBridge + Lambda(1분 주기)"로 적었다. **EC2의 두 번째 PM2 프로세스로 바꿀 것을 제안한다.**

| 판단 축 | Lambda | EC2 내 별도 프로세스 |
| --- | --- | --- |
| RDS 접근 | VPC 연결 필요 | 그냥 됨 |
| Bedrock 접근 (스위퍼는 리캡을 생성한다) | VPC Lambda라 **NAT Gateway(월 $32+) 또는 VPC 엔드포인트** 필요 | 퍼블릭 서브넷이라 그냥 됨 |
| 배포 산출물 | **2벌** — 기준점 결정기 코드가 두 곳에 존재 | 1벌 |
| 버전 스큐 위험 | API만 배포하고 Lambda를 빼먹으면 두 경로의 cutoff 계산이 갈린다 | 구조적으로 불가능 |
| 부하 | 데모 규모 수십 행 (r1 8장) | 동일 |
| 남은 작업량 (Freeze까지 1일) | 패키징·IAM·VPC·EventBridge | `pm2 start` 한 줄 |

**결정적인 건 세 번째 줄이다.** 절대 규칙 2번은 "기준점 결정기 밖에서 `page - 1` 계산 금지"인데, 배포 산출물이 두 벌이면 *같은 코드의 다른 버전*이 동시에 도는 상태가 만들어질 수 있다. 이건 grep CI로도 못 잡는다 — 코드는 한 벌인데 배포본이 두 벌이기 때문이다. 게이트 판정을 8/25에 한 번 하고 8/27에 리허설하는 일정에서, 그 사이 배포 누락 한 번이 판정 결과를 무효로 만든다.

> **r1 4.8절과 충돌하지 않는다.** 4.8절이 요구한 건 "실행 단위 분리"이지 "배포 대상 분리"가 아니다. 별도 진입점(`src/batch/sweeper/handler.ts`) · 별도 프로세스 · 별도 재시작 주기를 유지하므로 분리는 성립한다.

**스위퍼를 두 대에서 돌리려면 선점이 원자적이어야 한다 — 지금 코드는 그렇지 않다.**

한쪽에만 두면 그 인스턴스가 죽는 순간 세션 종료 감지가 멈춘다. 양쪽에서 돌리면 **같은 세션을 두 스위퍼가 동시에 집어 리캡을 중복 생성**할 수 있다(Bedrock 비용 2배 + FR-DAT-009 "사용자·도서당 1회" 위반).

현재 구현은 `findSweepTargets`(단순 SELECT) → `markPending`(별도 UPDATE) 2단계라 **그 사이에 경합 구간이 열려 있다.** 두 스위퍼가 같은 행을 SELECT한 뒤 각각 pending으로 바꾸고 각각 생성한다. 인스턴스가 1대일 때는 드러나지 않던 문제이며, **2.7절 이중화를 켜는 순간 실제 위험이 된다.**

**두 가지 처리 방법이 있다. Freeze 전에 골라야 한다.**

**(A) 원자적 선점으로 수정 — 액티브-액티브 유지**

두 스텝을 조건부 UPDATE 하나로 합치고, 서브쿼리에 **`FOR UPDATE SKIP LOCKED`를 반드시 둔다.** 이게 있어야 두 트랜잭션이 동시에 실행돼도 서브쿼리 단계에서 서로 잠긴 행을 건너뛰어 **애초에 겹치지 않는 후보 집합**을 갖는다.

```sql
-- 실제 스키마 기준: reading_session · recap_state (claimed_at 컬럼 없음)
UPDATE reading_session
   SET recap_state = 'pending'
 WHERE (device_id, book_id) IN (
       SELECT device_id, book_id FROM reading_session
        WHERE recap_state = 'none'
          AND last_activity_at < now() - interval '30 minutes'
        ORDER BY last_activity_at
        LIMIT 20
        FOR UPDATE SKIP LOCKED)
RETURNING device_id, book_id, session_epoch;
```

반환된 행만 처리한다. **`FOR UPDATE SKIP LOCKED`는 필수다.** 빼면 두 트랜잭션의 서브쿼리가 동시에 같은 행을 후보로 담을 수 있고, 바깥 `UPDATE ... WHERE (device_id, book_id) IN (...)`의 IN 목록은 서브쿼리가 실행된 시점에 이미 고정된 값이라 `recap_state` 조건을 다시 검사하지 않는다 — 첫 트랜잭션이 커밋돼 락이 풀리면 두 번째 트랜잭션도 그대로 UPDATE를 적용해 **중복 선점이 그대로 통과한다.** 즉 **최소 수정은 `findSweepTargets`와 `markPending`을 이 UPDATE ... RETURNING(`FOR UPDATE SKIP LOCKED` 포함) 하나로 합치는 것**이며, 스위퍼 전체를 다시 쓰는 작업이 아니다.

**(B) 스위퍼를 EC2 #1에서만 실행 — 코드 변경 없음**

파이프라인·평가 하네스와 같이 #1을 배치 담당 노드로 두고, #2에서는 스위퍼 프로세스를 띄우지 않는다. **#1이 죽으면 세션 종료 리캡 사전 생성이 멈추지만 서비스는 멈추지 않는다** — 저장분이 없으면 브리핑이 스트리밍 생성으로 폴백하도록 이미 설계돼 있다(UC-28 E1 · NFR-AI-016). 가용성 손실이 **기능 중단이 아니라 성능 저하**로 흡수된다.

> **권고 — Freeze까지 시간이 없으면 (B), 여유가 있으면 (A).** (A)가 옳은 방향이지만 스위퍼는 R2 파트의 핵심 경로이고, Freeze 하루 전에 손대는 것 자체가 위험을 만든다. (B)는 설정만으로 끝나며 나중에 (A)로 올려도 구성이 바뀌지 않는다. **어느 쪽이든 "그냥 양쪽에서 돌린다"만은 안 된다.**

> **⑦ 파이프라인과 ⑧ 평가 하네스는 어느 경우에도 EC2 #1에서만 실행한다.** 수동 트리거 배치라 스케줄 경합은 없지만, 두 대에서 각자 돌리면 공개 콘텐츠 쓰기가 충돌한다.

### 2.3 저장소 — RDS PostgreSQL + pgvector **[확정 제안]**

r1 443·596행이 "구체 엔진은 2회차"로 남겼고, CP0에서 팀이 이미 골랐다. 여기서는 배포 파라미터만 확정한다.

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 엔진 | PostgreSQL 16.x (pgvector 사용 가능한 최신 마이너) | 15도 가능하나 16이 pgvector 지원이 안정적 |
| 인스턴스 | **db.t4g.micro** | 「탁류」 1권 ≈ 페이지 수백 행. t4g.small은 과잉. 부족하면 콘솔에서 몇 분 만에 승급 가능 |
| 스토리지 | gp3 20GB, 오토스케일링 OFF | 실데이터 + 임베딩 + 로그 전부 합쳐 수백 MB 수준 |
| 가용성 | **Multi-AZ** (AZ-a 주 / AZ-c 대기) | EC2를 2 AZ로 나눈 이상 DB가 단일 AZ면 이중화가 성립하지 않는다 — 2.7절 |
| 네트워크 | 프라이빗 서브넷 · 퍼블릭 액세스 OFF · SG는 EC2 SG에서만 5432 허용 | 인터넷 노출 0 |
| 백업 | 자동 백업 7일 + 8/24·8/27 수동 스냅샷 | 스냅샷은 리허설 직전에 |
| **자동 마이너 업그레이드** | **OFF** | 켜두면 유지관리 창에 재부팅이 들어온다 |
| **유지관리 창** | **8/25~8/28 밖으로** (예: 화 09:00 UTC) | 게이트 판정 주간에 재부팅이 잡히면 그날을 잃는다 |

**벡터 인덱스를 만들지 않는다 [확정 제안]**

pgvector에서 HNSW·IVFFlat은 **근사(approximate)** 인덱스다. 우리 검색은 항상 `WHERE page_no <= K` 사전 필터가 붙는데(r1 5.3절, D5), 근사 인덱스와 선택도 높은 사전 필터가 결합하면 후보가 필터에서 대량 탈락해 **top-N 6개를 못 채우거나 엉뚱한 페이지가 올라온다.** 그 손실은 항상 기준점 근처, 즉 질문이 가장 많이 나오는 구간에서 발생한다 — D11이 청크 1:1을 지킨 것과 정확히 같은 이유다.

게이트 관점에서 더 중요한 건 방향이다. 이 손실은 스포일러 누설(FR-SPL-002 🚦)이 아니라 **부당 거절(FR-QNA-007 🚦, 30건 중 27건)** 쪽으로 나타난다. 즉 안전한 실패가 아니다.

수백 행에 대한 정확 검색(`ORDER BY embedding <=> $1 LIMIT 6`)은 순차 스캔으로 밀리초 단위다. **인덱스 없이 정확 검색으로 간다.** 도서가 수십 권이 되기 전까지 이 결정은 유효하다.

### 2.4 프론트 배포와 TLS — 여기가 유일한 실질적 분기점

NFR-SEC-002(모든 통신 TLS 1.2 이상, P0)는 도메인이 없으면 만족시킬 수 없다. EC2 퍼블릭 IP에는 인증서를 발급받을 수 없기 때문이다. 두 안이 있다.

**A안 — 도메인 없이 (CloudFront 기본 인증서)** ★ 기본 제안

| 항목 | 구성 |
| --- | --- |
| 클라이언트 TLS | CloudFront 기본 도메인 `dxxxx.cloudfront.net` + 기본 인증서 (무료, 도메인 불필요) |
| 정적 | S3 버킷(퍼블릭 차단) ← OAC ← CloudFront 기본 behavior, 캐싱 활성 |
| API | behavior `/api/*` → EC2 오리진(HTTP 80), **CachingDisabled** + AllViewerExceptHostHeader |
| 오리진 보호 | EC2 SG 인바운드 80을 관리형 프리픽스 리스트 `com.amazonaws.global.cloudfront.origin-facing`으로 제한 + CloudFront 커스텀 헤더 시크릿을 Nginx에서 검증 |
| 비용 | 사실상 $0~2 |
| 남는 간극 | **CloudFront ↔ EC2 구간이 HTTP다.** AWS 백본 내부 + IP·헤더 이중 제한이지만 NFR-SEC-002의 문자 그대로는 아니다 |

**B안 — 도메인 구매 (종단 TLS)**

| 항목 | 구성 |
| --- | --- |
| 도메인 | Route 53 등록 (.com 연 $14 내외) + 호스팅 영역 월 $0.50 |
| 클라이언트 TLS | CloudFront + ACM 인증서(us-east-1, 무료) — `app.example.com` |
| 오리진 TLS | **ALB 리스너를 443 + ACM 인증서로 교체** (2.7절). `api.example.com` A레코드(별칭) → ALB, CloudFront 오리진 프로토콜 HTTPS |
| 비용 | 첫 해 약 $15 + 월 $0.5 (**ALB는 이미 있으므로 추가 비용 없음**) |
| 이점 | NFR-SEC-002 완전 충족 · 발표 자료에 IP가 아닌 도메인 · **인증서 관리가 ALB 한 곳으로 모임** |

> **ALB가 있어서 B안이 오히려 쉬워졌다.** EC2 2대에 Let's Encrypt를 각각 깔고 갱신을 관리하는 것보다, **ALB에 ACM 인증서 1장(무료·자동 갱신)**을 붙이는 쪽이 작업량도 운영 부담도 적다. 인증서를 앱 서버가 아니라 진입점에서 끝내는 것이 정석이기도 하다.

**→ [확정 8/21] A안으로 올리고, 8/26 예비일에 여유가 있으면 B안으로 승격한다.**

승격은 되돌릴 일이 없다 — CloudFront 배포·S3·EC2를 그대로 두고 **대체 도메인(CNAME)과 ACM 인증서만 추가**하면 되고, 기존 `*.cloudfront.net` 주소도 계속 살아 있다. 승격 판단 기한은 **8/26**이다. CP6(8/27) 리허설에 새 도메인이 처음 등장하는 상황은 만들지 않는다.

> **승격 시 잊기 쉬운 것** — 인증서가 **두 장 필요하고 리전이 다르다.** CloudFront용은 반드시 **us-east-1**(서울에서 발급하면 목록에 안 뜬다), ALB용은 **ap-northeast-2**다. 같은 도메인이라도 각 리전에서 따로 발급받아야 한다.

> **A안의 남은 간극을 발표에서 어떻게 말할 것인가** — NFR-SEC-002는 P0이고 A안은 오리진 구간이 HTTP다. 숨기지 말고 "클라이언트 구간은 TLS 1.2+ 강제, 오리진 구간은 AWS 백본 내부에서 프리픽스 리스트 + 공유 시크릿 이중 제한, 정식 운영에서는 종단 TLS로 승격"이라고 **설계 근거와 함께 밝히는 편**이 낫다. 게이트가 아닌 조항에서 트레이드오프를 인지하고 있다는 게 오히려 설계 성숙도로 읽힌다.

**SSE가 CloudFront를 통과하게 하는 설정** (NFR-PERF-002 🚦 · 008이 여기 걸린다)

| 지점 | 설정 |
| --- | --- |
| CloudFront `/api/*` | 캐시 정책 `CachingDisabled` · **압축 비활성** · 오리진 응답 타임아웃 60초로 상향 |
| Nginx | `proxy_buffering off;` `proxy_cache off;` `chunked_transfer_encoding on;` `proxy_read_timeout 300s;` |
| 앱 응답 헤더 | `Content-Type: text/event-stream` · `Cache-Control: no-cache, no-transform` · **`X-Accel-Buffering: no`** |
| 앱 | 15초마다 keepalive 코멘트(`: ping\n\n`) 전송 |

`no-transform`과 압축 비활성이 빠지면 중간에서 버퍼링이 붙어 **첫 토큰이 스트림 끝까지 지연된다.** 게이트가 로컬에서는 통과하고 배포 환경에서만 실패하는 전형적인 지점이므로, 8/23 실측 항목에 넣는다.

### 2.5 S3의 용도 — 원문은 서빙하지 않는다 **[확정 제안 · r1 352·783행 마감]**

| 버킷/프리픽스 | 내용 | 접근 |
| --- | --- | --- |
| `ssabi-web/` | 프론트 빌드 산출물 | CloudFront OAC만 |
| `ssabi-assets/source/` | 「탁류」 원문 원본 (파이프라인 입력) | EC2 인스턴스 역할만 |
| `ssabi-assets/backup/` | DB 덤프 (수동, 8/24·8/27) | EC2 인스턴스 역할만 |
| `ssabi-assets/eval/` | 평가 하네스 실행 기록 (NFR-AI-009) | EC2 인스턴스 역할만 |

**페이지 본문은 S3에 두지 않는다.** 검색과 조회가 전부 `page_no <= K` 단일 SQL로 끝나야 하므로(r1 5.3절) 페이지는 DB에만 존재한다. S3의 원문 원본은 파이프라인 입력이자 재현용 아카이브이며, **어떤 경로로도 클라이언트에 서빙되지 않는다** — 퍼블릭 액세스 차단 + 버킷 정책으로 구조적으로 막는다(NFR-SEC-005).

### 2.6 세션 리캡 캐시 — DB 테이블 **[해소 · r1 479행 마감 · 이미 구현됨]**

r1은 "메모리 / 단명 테이블"을 열어두고 실행 모델과 함께 정하라고 했다. 실행 모델이 정해졌으므로 답이 나온다.

- API가 `cluster 2`로 뜬다 → 인메모리면 캐시 적중률이 절반으로 떨어진다
- **스위퍼가 별도 프로세스다** → 스위퍼가 만든 저장분을 API 프로세스의 메모리 캐시가 알 수 없다
- PM2 `reload` 한 번에 캐시가 전부 날아간다 → 배포 직후 리허설에서 LLM 호출이 갑자기 늘고, NFR-PERF-003(재사용 1.0초) 측정이 흔들린다

→ **`session_recap_cache` 테이블.** 이미 `002_reading_state.sql`에 존재·병합돼 있다 — 새로 결정할 사안이 아니라 배포 파라미터 확인 항목이다. 실제 스키마: PK(device_id, book_id, cutoff_page) + `expires_at` 컬럼(`session_epoch` 컬럼은 없다 — v0.4까지 이 문서가 잘못 서술했다). **무효화는 `expires_at` TTL 비교**로 하고(`ix_session_recap_cache_expiry` 인덱스), 삭제는 스위퍼가 세션 종료 판정 시 대화 이력과 함께(A7). FR-DAT-010의 "영구 저장 금지"는 *행의 수명*에 대한 요구이지 저장 매체에 대한 요구가 아니므로 충족된다.

> ElastiCache는 쓰지 않는다. 최소 인스턴스가 월 $12~15인데, 우리가 캐시에서 원하는 건 **프로세스 간 공유**이지 처리량이 아니다. 그건 이미 있는 RDS가 한다.

### 2.7 이중화 구성 — EC2 2대 · ALB · RDS Multi-AZ **[확정]**

가용성을 AZ 단위로 확보한다. 인스턴스 1대·Single-AZ 구성은 **인스턴스나 AZ 하나가 죽으면 서비스 전체가 죽는다** — 데모 기간에 그럴 확률이 낮다는 것과, 구조적으로 그렇게 되어 있다는 것은 다른 문제다.

| 계층 | 구성 |
| --- | --- |
| 진입 | **ALB** — 퍼블릭 서브넷 AZ-a·AZ-c 양쪽에 노드. CloudFront의 오리진이 된다 |
| 앱 | **EC2 2대** — `ssabi-app-a`(AZ-a) / `ssabi-app-c`(AZ-c). 사양·구성 동일 |
| DB | **RDS Multi-AZ** — AZ-a 주 / AZ-c 대기, 장애 시 자동 장애 조치 |

**세 계층을 함께 가야 성립한다.** EC2만 2 AZ로 나누고 DB를 AZ-a 단일로 두면, AZ-a가 죽는 순간 AZ-c의 EC2도 DB를 잃어 서비스가 멈춘다. **비용만 늘고 가용성은 그대로인 구성**이 되므로, 이중화를 한다면 RDS Multi-AZ가 선택이 아니라 전제다.

**이 구성이 가능한 이유는 애플리케이션이 무상태이기 때문이다.** 상태는 전부 RDS에 있고, 세션 리캡 캐시도 DB 테이블이다(2.6절). 어느 인스턴스가 요청을 받아도 같은 기준점·같은 리캡이 나오므로 **스티키 세션이 필요 없다.** 세션 캐시를 인메모리로 뒀다면 여기서 캐시 적중률이 절반이 되거나 스티키 세션을 붙여야 했다 — 2.6절 결정이 여기서 값을 한다.

**ALB 설정에서 놓치면 안 되는 것**

| 항목 | 값 | 이유 |
| --- | --- | --- |
| **유휴 타임아웃** | **300초 이상** (기본 60초) | 기본값이면 **SSE 스트림이 1분에 끊긴다.** 리캡·챗봇이 게이트(NFR-PERF-002 🚦·008)라 여기서 실패하면 판정이 날아간다 |
| 대상 그룹 헬스체크 | `/health`, 15초 간격, 2회 실패 시 제외 | 죽은 인스턴스로 요청이 가지 않게 |
| 스티키 세션 | **끈다** | 무상태라 불필요. 켜면 한쪽으로 쏠려 이중화 효과가 준다 |
| 교차 영역 부하 분산 | 켠다 (ALB 기본) | |
| 리스너 | HTTP 80 ← CloudFront | B안 승격 시 443 + ACM 인증서로 교체 |

> **ALB 도입이 B안(도메인) 승격을 더 매력적으로 만든다.** EC2 2대에 Let's Encrypt 인증서를 각각 깔고 갱신하는 것보다, **ALB에 ACM 인증서 1장(무료·자동 갱신)**을 붙이는 쪽이 훨씬 깔끔하다. 8/26 판단 시 이 점을 함께 본다.

**무중단 배포가 실제로 가능해진다** — 한 대씩 순차 배포(#1 배포 → 헬스체크 통과 → #2 배포)하면 서비스 중단이 0이다. 6.2절 배포 스크립트를 루프로 바꾼다.

**EC2 #1을 배치 담당 노드로 지정한다** — 파이프라인(⑦)과 평가 하네스(⑧)는 #1에서만 실행한다. **스위퍼는 2.2절의 (A)/(B) 결정에 따른다** — 원자적 선점을 구현하면 양쪽, 아니면 #1에서만. 현재 코드 기준으로는 양쪽에서 돌리면 안 된다.

## 3. 네트워크

| 리소스 | 구성 |
| --- | --- |
| VPC | `10.0.0.0/16`, 신규 생성 (기본 VPC 사용 금지 — 정리할 때 통째로 지우기 위해) |
| 퍼블릭 서브넷 | `10.0.1.0/24` (AZ-a), `10.0.2.0/24` (AZ-c) — **ALB 노드 + EC2 각 1대** |
| 프라이빗 서브넷 | `10.0.11.0/24` (AZ-a), `10.0.12.0/24` (AZ-c) — RDS 주/대기 |
| IGW | 있음 |
| **NAT Gateway** | **없음** |

**EC2를 퍼블릭 서브넷에 두는 것이 NAT를 피하는 방법이다.** 앱이 Bedrock·ECR·패키지 저장소로 나가야 하는데, 프라이빗 서브넷에 두면 NAT Gateway가 필요해진다 — 시간당 $0.045 + 데이터 처리 $0.045/GB로 **아무 일도 하지 않아도 월 $35 이상**, 2 AZ면 2배다. 이중화로 늘어난 비용을 여기서 상쇄한다.

인터넷에서 EC2로 직접 들어오는 경로는 보안 그룹으로 닫는다 — **인바운드는 ALB에서 오는 것만 허용**하므로, 퍼블릭 서브넷에 있다는 것은 *나갈 수 있다*는 뜻이지 *들어올 수 있다*는 뜻이 아니다.

**보안 그룹**

| SG | 인바운드 |
| --- | --- |
| `sg-alb` | 80 ← CloudFront 관리형 프리픽스 리스트 (B안 승격 시 443) |
| `sg-ec2` | 80 ← **`sg-alb`** (SG 참조) · 22 ← **팀원 IP만** |
| `sg-rds` | 5432 ← **`sg-ec2`** (SG 참조, CIDR 아님) |

**3단 체이닝이다.** CloudFront → ALB → EC2 → RDS 각 구간이 앞 단계의 SG만 신뢰하므로, 중간을 건너뛴 직접 접근이 구조적으로 막힌다. EC2에 공인 IP가 붙어 있어도 80 인바운드가 `sg-alb`로만 열려 있어 외부에서 직접 때릴 수 없다.

22번을 0.0.0.0/0으로 열지 않는다. 팀원 4명이 각자 다른 네트워크에 있어 IP가 바뀌면 귀찮은데, 그때는 CIDR을 넓히지 말고 **EC2 Instance Connect Endpoint**(무료)를 쓰거나 그때그때 규칙을 갱신한다.

## 4. 보안 · 시크릿 **[r1 108·235·671·673행 마감]**

### 4.1 정적 자격증명을 서버에 두지 않는다 **[확정 제안]**

TECH_STACK.md의 프로덕션 `.env` 예시에 `AWS_ACCESS_KEY_ID`·`AWS_SECRET_ACCESS_KEY`가 들어 있다. **EC2에서는 이 두 줄을 지운다.**

| 대상 | 방법 |
| --- | --- |
| Bedrock · S3 | **IAM 인스턴스 프로파일**. SDK가 자동으로 집어간다. 코드 변경 0 |
| DB 비밀번호 | **SSM Parameter Store SecureString** (무료). 부팅 스크립트가 조회해 환경변수로 주입 |
| CloudFront 오리진 시크릿 | 동일 |

Secrets Manager는 시크릿당 월 $0.40이라 나쁘지 않지만, 우리가 쓰는 시크릿이 2~3개라 Parameter Store로 충분하다.

**IAM 역할 정책 (최소 권한)**

```
bedrock:InvokeModel, bedrock:InvokeModelWithResponseStream
  → Resource: 실제 쓰는 모델/프로필 ARN 3개만 (Sonnet 4.5 · Haiku 4.5 · Titan V2)
s3:GetObject, s3:PutObject  → arn:aws:s3:::ssabi-assets/*
ssm:GetParameter(s)         → /ssabi/prod/* (+ kms:Decrypt)
logs:CreateLogStream, logs:PutLogEvents
```

Bedrock을 `Resource: *`로 열지 않는 이유는 보안보다 **비용 사고 방지**다. 모델 ARN을 못박아두면 실수로 상위 모델을 호출하는 코드가 배포돼도 거기서 막힌다.

> **개인 키 정리** — 개발 중 발급해 쓰던 Bedrock 개인 키·베어러 토큰은 EC2 배포와 함께 비활성화한다. 서버에는 인스턴스 역할만 남는다.

### 4.2 TLS

2.4절 참조. A안/B안 어느 쪽이든 클라이언트 구간은 TLS 1.2 이상이 강제된다(CloudFront 최소 프로토콜을 `TLSv1.2_2021`로 설정).

### 4.3 원문 보호 (NFR-SEC-005 P1)

### 4.4 디바이스 식별자 **[r1 671행 — 부분 마감]**

**전달 방식은 CP0에서 이미 동결됐다. 이 문서는 그것을 바꾸지 않는다.**

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 전달 | **`X-Device-Id: <uuid>` 요청 헤더** | `API_CONTRACT.md` 2장 — CP0 동결 계약. 라우트가 이미 이 값을 읽고 있다 |
| 검증 | 값 일치만. 계정이 없으므로 그 이상은 없다 | NFR-SEC-001 P1 |
| 발급 주체 | **[해소 · 8/20 팀 결정]** — **클라이언트가 최초 실행 시 `crypto.randomUUID()`로 발급.** `frontend/src/services/api.ts`의 `ensureDeviceId()`에 구현·병합 완료 | team-sync-r4.md §4.8 — `API_CONTRACT.md` 원문("서버가 첫 요청 시 발급")과 다르지만, R2·R3 라우트가 이미 헤더 부재 시 400으로 거절하도록 구현돼 있어 서버가 발급할 자리가 실제로 없었다. 서버 쪽 수정 없이 맞출 수 있는 클라이언트 발급으로 팀 결정 |

> **v0.2 초안의 쿠키 방식(`Set-Cookie: did=...; HttpOnly`)은 철회한다.** 배포 관점에서는 쿠키가 낫다고 봤지만 — HttpOnly면 XSS로 못 읽고, CloudFront 단일 오리진이라 서드파티 쿠키 문제도 없다 — **이미 동결된 계약을 배포 문서가 일방적으로 바꿀 수는 없다.** HttpOnly 쿠키는 JS가 읽지 못하므로 프론트가 헤더에 실어 보내는 현재 방식과 **양립 불가**이고, 채택하면 R2 라우트 3개 · R3 `/chat` · R4 프론트를 Freeze 전에 전부 고쳐야 한다.
>
> 쿠키로 가는 것이 실제로 더 낫다고 판단되면 **Freeze 이후 별건으로, R3·R4 통지와 함께** 올린다. 배포 설계 문서에서 조용히 확정할 사안이 아니다.

**헤더 방식이 안고 가는 위험 — 기록해 둔다.** 헤더로 보내려면 프론트가 식별자를 JS가 읽을 수 있는 곳(localStorage 등)에 저장해야 하고, **XSS가 나면 그대로 읽힌다.** 진도 기록이 노출되는 범위이며 계정·결제 정보는 없다. r1 671행이 "식별자 탈취 시의 진도 조회 위험은 P1 수준에서 수용"이라고 정한 그 위험에 해당하므로 **수용하되, 수용했다는 사실을 남긴다.** 정식 서비스에서 계정 체계가 들어올 때 함께 재설계할 지점이다.

## 6. CI/CD

### 6.1 CI — `ci.yml` (PR · push 시)

```
1. typecheck   : npm run build
2. lint        : npm run lint
3. test        : npm test
4. 금칙 검사   : scripts/check-forbidden.sh   ★
```

**4번이 이 프로젝트의 CI다.** 절대 규칙 10개 중 정적으로 잡히는 것을 grep으로 막는다.

```bash
#!/usr/bin/env bash
set -euo pipefail
fail=0
chk() { # 설명, 패턴, 제외경로
  if grep -rnE "$2" src --include='*.ts' --include='*.tsx' \
       | grep -vE "$3" | grep -v '\.test\.ts'; then
    echo "❌ $1"; fail=1
  fi
}

# 규칙 2 — page-1 / 퍼센트 계산은 기준점 결정기 안에서만
chk "page-1 계산이 cutoff 밖에 있음" \
    'current_page[[:space:]]*-[[:space:]]*1|page[[:space:]]*-[[:space:]]*1' \
    'modules/reading-state/cutoff'
chk "진도 % 계산이 cutoff 밖에 있음" \
    '/[[:space:]]*total_pages' \
    'modules/reading-state/cutoff'

# 규칙 3 — 프롬프트 지시로 상한을 걸지 않는다
chk "프롬프트로 스포일러 차단을 지시함" \
    '스포일러(를)?[[:space:]]*(쓰지|언급하지|포함하지)|do not (write|reveal) spoilers' \
    'XXXX_no_exclusion'

# 규칙 4 — 게이트웨이 우회
chk "Bedrock SDK 직접 호출" \
    '@aws-sdk/client-bedrock-runtime' \
    'modules/llm-gateway'

# 규칙 8 — 클라이언트가 기준점을 보내는 API
chk "요청 본문에 cutoff 수용" \
    'req\.(body|query)[^;]*cutoff' \
    'XXXX_no_exclusion'

exit $fail
```

> **이 CI 결과가 게이트 증거다.** NFR-SEC-006 판정 ①은 "코드 작성자 외 1명이 리뷰하고 **기록**"인데, CI 로그를 아티팩트로 보관하면 교차 리뷰(CP4)의 보조 증거가 된다. 사람이 놓치는 걸 잡는 게 아니라, **사람이 봤다는 사실을 기계가 증명한다.**

### 6.2 CD — `deploy.yml` (main push, 수동 승인)

Freeze(8/22) 전후로 성격이 달라야 한다.

| 시점 | 트리거 |
| --- | --- |
| ~8/22 | main push 시 자동 |
| 8/23~ | **`workflow_dispatch` 수동만** + main 브랜치 보호 |

```
[백엔드]  SSH → EC2
   git pull → npm ci → npm run build → pm2 reload ssabi-api ssabi-sweeper
   → /health 확인 → 실패 시 직전 릴리스로 롤백
[프론트]  Actions에서 vite build → aws s3 sync → CloudFront invalidation
```

`pm2 restart`가 아니라 **`pm2 reload`**를 쓴다. cluster 모드에서 워커를 하나씩 교체하므로 진행 중인 SSE 연결이 전부 동시에 끊기지 않는다.

**빌드는 EC2에서 한다.** 아티팩트를 Actions에서 만들어 옮기는 쪽이 정석이지만, Freeze까지 하루 남은 시점에 산출물 전달 경로를 새로 만드는 건 이득보다 리스크가 크다. t3.medium(4GB)에서 tsc 빌드는 문제없다. 프론트만 Actions 빌드인 이유는 어차피 S3로 가야 해서다.

**배포 키** — GitHub Actions Secrets에 EC2 SSH 개인키와 배포용 IAM 사용자 키(S3 sync + CloudFront invalidation 권한만). 이 IAM 사용자에는 Bedrock 권한을 주지 않는다.

## 10. 발표일 가용성 — NFR-AVL-003 **[v0.3 개정 · r1 669행 마감]**

> **네트워크 전제 (8/21 확인)** — 발표장은 무선이지만 **불안정할 우려는 낮다**고 판단했다. 따라서 v0.2에서 로컬 스택으로 올렸던 시연 매체를 **prod로 되돌린다.** 로컬 스택은 폐기하지 않고 **폴백으로 유지**한다.

조항은 존치하되 게이트에서는 내려갔다(D12). 판정 대상은 없지만 대비는 한다.

### 10.1 시연 매체

| 구분 | 매체 |
| --- | --- |
| **시연 (8/28)** | **prod (CloudFront → EC2 → RDS)** — 실제 배포된 것을 보여주는 게 원칙이다 |
| 게이트 판정 · 성능 측정 (8/25) | 동일하게 prod (NFR 5.5 "로컬 측정 금지") |
| 폴백 | 노트북 로컬 스택 (10.3절) |

측정과 시연이 같은 환경이라는 게 이 구성의 이점이다. 발표에서 제시하는 성능 수치가 지금 화면에서 도는 것과 같은 시스템에서 나온 값이 된다.

### 10.2 네트워크 의존을 줄이는 것이 1차 방어다

**가장 값싼 대비는 애초에 호출을 안 하는 것이다.** 시연 위치의 저장 리캡을 사전 주입하면(UC-19 3번) 정상 동선에서 **실시간 LLM 호출이 0회**가 된다. 남는 외부 의존은 챗봇 질의 1~2건뿐이다.

여기에 스트리밍 구간의 방어를 더한다.

| 조치 | 이유 |
| --- | --- |
| SSE keepalive 15초 (2.4절) | 중간 장비의 유휴 연결 정리를 막는다 |
| **클라이언트 SSE 재연결** — 끊기면 재시도 후 실패 시 명시적 안내 | 끊긴 SSE는 **"생성 중인 것처럼 보이면서 영원히 오지 않는다."** 무한 로딩이 발표 중 최악의 실패 모습이다. 타임아웃(예: 15초 무수신)을 두고 안내로 전환한다 |
| 정적 자산 CloudFront 캐시 | 화면 전환에서 원본까지 갈 일이 없다 |
| 시연 직전 워밍업 1회 | RDS 커넥션 풀·PM2 워커·CloudFront 엣지 캐시를 데워둔다. 첫 요청만 느린 현상을 발표에서 보이지 않는다 |

> **클라이언트 SSE 타임아웃은 R4 작업이다.** 서버가 아무리 잘 스트리밍해도 클라이언트가 무한 대기하면 소용이 없다. Freeze 전에 확인할 것.

### 10.3 폴백 3단

| 단계 | 수단 | 커버 |
| --- | --- | --- |
| **0차 — 호출 회피** | 시연 위치 저장 리캡 사전 주입 | 정상 동선 실시간 LLM 호출 0회. **챗봇 외 전 기능이 LLM 장애와 무관해진다** (NFR-AVL-002) |
| **1차 — 로컬 스택** | 노트북 `docker-compose`(pgvector Postgres + API + 정적 프론트) + prod DB 덤프. 프론트 `API_BASE`를 환경변수로 전환 | 발표장 인터넷이 죽어도 읽기·관계도·인물·저장 리캡 전부 동작. Bedrock이 필요한 챗봇만 불가 |
| **2차 — 최후** | 챗봇 시연 구간 사전 녹화 | 기준점 전후 같은 질문/다른 답 시연을 영상으로 |

**1차가 실질적 안전망이다.** 로컬 Postgres를 pgvector 이미지로 쓴 개발 환경 선택이 여기서 회수된다 — 그때 만든 `docker-compose.yml`이 그대로 발표일 폴백이 된다. 추가로 필요한 준비는 **8/27에 prod 덤프를 한 번 받아두는 것**뿐이다.

> **식별자가 헤더 방식이라 폴백에 유리하다 (4.4절).** 폴백은 `http://192.168.x.x`인데, **커스텀 헤더는 HTTPS가 아니어도 그대로 동작한다.** 쿠키였다면 `Secure` 플래그 때문에 평문 HTTP에서 저장이 안 돼 별도 토글이 필요했을 것이다. 다만 프론트가 식별자를 **오리진 단위로** 저장한다면(localStorage 등) prod 주소와 폴백 주소가 서로 다른 오리진이라 **진도가 이어지지 않는다** — 폴백 전환 시 같은 독자로 보이지 않는다. 8/27 리허설에서 확인할 것.

## 12. 채택하지 않은 구성과 그 근거

> 이 장은 "왜 더 갖추지 않았는가"에 대한 기록이다. **근거 없이 안 쓴 것과 판단해서 안 쓴 것은 다르고, 그 차이는 문서로만 증명된다.** 아래 항목은 전부 예산 안에 들어오지만 채택하지 않았다 — 즉 비용이 아니라 판단이 이유다.
>
> 가용성 이중화(EC2 2 AZ · ALB · RDS Multi-AZ)는 **채택했다.** 2.7절 참조.

### 12.1 ECS / Fargate — 미채택 **[8/21 결정]**

컨테이너 오케스트레이션으로 전환하는 안을 검토하고 **EC2 + PM2를 유지하기로 했다.**

**ECS가 우리 설계에 실제로 나은 점이 있었다.** 특히 배포 산출물 동일성이 그렇다. 2.2절에서 스위퍼를 Lambda에서 뺀 핵심 논거가 "산출물이 두 벌이면 기준점 결정기 코드 버전이 갈릴 수 있다"였는데, ECS라면 같은 이미지 태그에 커맨드만 다르게 주는 방식으로 **두 프로세스가 같은 코드임을 이미지 다이제스트로 증명**할 수 있다. 지금의 PM2 방식은 "같은 서버에서 같이 배포했으니까"라는 관례에 기댄다. 이건 ECS 쪽이 구조적으로 낫다.

그럼에도 채택하지 않은 이유는 셋이다.

| # | 이유 |
| --- | --- |
| 1 | **팀에 ECS 경험자가 없다.** ECS의 난이도는 평상시가 아니라 장애 시에 드러난다 — 태스크가 재시작을 반복하는데 로그가 안 보이거나, 실행 역할과 태스크 역할을 혼동해 Bedrock 호출만 권한 오류가 나는 유형이다. EC2라면 SSH로 5분에 끝날 일이 반나절이 된다 |
| 2 | **그 반나절이 8/25 게이트 판정 주간에 놓인다.** 도입 시점이 Freeze(8/22) 직후이고, 판정 실패 시 복구 시간이 없다 |
| 3 | **반복 속도가 떨어진다.** 8/23~27은 4명이 트러블슈팅하는 구간인데, EC2는 로그 확인·수정·재시작이 초 단위이고 Fargate는 빌드→푸시→리비전→롤링이 매번 3~5분이다. 파이프라인(⑦)·평가 하네스(⑧)처럼 **반복 실행하는 수동 배치**가 특히 불리하다 |

**전제가 하나만 달랐어도 결론이 달랐다.** 팀에 경험자가 있고 그 사람이 인프라를 전담했다면 Fargate가 나은 선택이었다. 채택 여부를 가른 건 기술적 우열이 아니라 **일정 안에서 감당 가능한가**였다.

> **정식 전환 시의 경로** — ① 프로덕션 Dockerfile(멀티스테이지) ② ECR ③ Task Definition — 실행 역할/태스크 역할 분리 ④ ALB + **SSE를 위한 유휴 타임아웃 300초 이상** ⑤ 퍼블릭 서브넷 + `assignPublicIp`로 NAT 회피(프라이빗에 두면 NAT 또는 인터페이스 엔드포인트로 월 $30+가 붙는다) ⑥ `run-task` 커맨드 오버라이드로 배치 실행. **난이도의 90%는 ECS가 아니라 이미지와 네트워킹에 있다.**

### 12.2 Auto Scaling Group — 미채택

인스턴스 2대를 ASG(min=max=2)로 관리하는 안을 검토했다. 자동 대체라는 이득이 있지만, **인스턴스 교체 시 앱을 자동으로 배포해 주는 장치**(사용자 데이터 스크립트나 AMI 굽기)가 함께 필요하고 그게 실질 작업량이다. 8/22 Freeze까지의 일정에서 감당 범위를 넘는다.

대신 **CloudWatch 알람의 자동 복구 액션**으로 하드웨어 장애 시 같은 볼륨으로 재기동되게 해 둔다(5장). 인스턴스가 통째로 사라지는 경우는 커버하지 못하지만, 그때는 남은 1대가 ALB 뒤에서 계속 받는다 — **이중화가 이미 그 역할을 한다.**

정식 운영에서는 ASG + 시작 템플릿 + AMI 파이프라인이 맞는 방향이다.

### 12.3 ElastiCache · OpenSearch — 미채택

| 항목 | 근거 |
| --- | --- |
| ElastiCache | 캐시에서 원하는 건 처리량이 아니라 **프로세스 간 공유**이고, 그건 이미 있는 RDS가 한다 (2.6절). 인스턴스가 2대가 되어도 결론은 같다 — 공유 지점이 하나이기만 하면 된다 |
| OpenSearch Serverless | **8/19에 이미 기각됐다** — 예산과, 페이지 범위 필터를 자동화에 넘기지 않는다는 통제권 논거(r1 5.3절) |

### 12.4 지금 구성이 감당하는 부하와 다음 단계

| 부하 수준 | 필요한 변경 |
| --- | --- |
| 데모 (동시 수 명) | **현재 구성 그대로** |
| 동시 수십~수백 명 | **인스턴스 추가만.** ALB 대상 그룹에 붙이면 끝 — 코드 변경 없음 |
| 동시 수천 명 | RDS 읽기 전용 복제본 · 인스턴스 클래스 승급 · ASG 자동 확장 |
| 도서 수십 권 | 벡터 인덱스 도입 검토 — 단, 사전 필터와의 recall 문제를 재확인해야 한다 (2.3절) |
| 상시 운영 | ECS/Fargate + IaC + ASG (12.1·12.2절) |

**두 번째 줄에 코드 변경이 없다는 점이 이 설계의 실질적 확장성이다.** 애플리케이션이 무상태이고 세션 리캡 캐시가 DB 테이블이라(2.6절) 인스턴스를 몇 대로 늘리든 동작이 같다. 캐시를 인메모리로 뒀다면 스티키 세션을 붙이거나 캐시 계층을 새로 만들어야 했다 — **확장성은 인스턴스를 늘린 데서 오는 게 아니라, 늘려도 되는 상태로 만들어 둔 데서 온다.**
